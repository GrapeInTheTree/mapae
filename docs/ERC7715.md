# Mapae and ERC-7715

ERC-7715 (`wallet_requestExecutionPermissions`) is the wallet-side request surface for scoped
permissions: an app asks the wallet for bounded authority, the user approves once in wallet UI,
and the app receives an opaque context it can redeem without further prompts. ERC-7710 is its
contract-side counterpart — which Mapae implements.

No wallet on GIWA exposes ERC-7715 today; GIWA Wallet is unreleased and its documentation says
nothing about permissions. This document exists so that the day a wallet wants to, the mapping is
one page rather than a design project. **Mapae deliberately builds no wallet** — the primitive's
job is to be what wallets call.

## The mapping

A conformant response to `wallet_requestExecutionPermissions` maps onto Mapae as follows.

| ERC-7715 field | Mapae realisation |
|---|---|
| `context` | `abi.encode(Delegation[])` — the permission context `redeemDelegations` consumes, leaf first |
| `delegationManager` | `MapaeDelegationManager`, `0xfd0fCCCcF8071852783b5133b3CC47461f33e6Cd` on GIWA Sepolia |
| `from` | the `MapaeAccount` (or, on the EIP-7702 path, the user's EOA itself) |
| `to` | the session account the app controls — the delegation's `delegate` |
| `dependencies` | `[{factory: MapaeAccountFactory, factoryData: createAccount(owner, salt, consent)}]` when the account is counterfactual; empty once deployed |
| `permission: {type: "erc20-token-periodic"}` | `ERC20PeriodTransferEnforcer`, terms `token ‖ periodAmount ‖ periodDuration ‖ startDate` |
| `rules: [{type: "expiry", data: {timestamp}}]` | `TimestampEnforcer`, terms `0 ‖ uint128(timestamp)` |

Two Mapae capabilities have no ERC-7715 vocabulary yet, which is the interesting part:

**Proposed permission type — `dojang-verified`**

```json
{
  "type": "dojang-verified",
  "isAdjustmentAllowed": false,
  "data": {"attesterId": "0xd99b42e7…", "principal": "0x…"}
}
```

Realised by `DojangVerifiedEnforcer` with terms `attesterId(32) ‖ principal(20)`. Semantics: the
permission is valid only while `principal` holds a live Verified Address attestation from the
named issuer, evaluated per redemption. This is the piece that makes an ERC-7715 grant *insurable*
— the wallet UI can render it as literally: *"valid only while your Upbit verification stands."*

**Proposed rule type — `allowed-payees`**

```json
{"type": "allowed-payees", "data": {"payees": ["0x…", "0x…"]}}
```

Realised by `AllowedPayeeEnforcer`. ERC-7715's example permissions bound *how much*; nothing in
the draft bounds *to whom*. For payments, "to whom" is the half a person actually reasons about.

## What a GIWA Wallet implementation would do

1. Receive the request; render the caveats in plain language — the terms layouts are fixed-offset
   packed bytes precisely so a wallet can decode and display every bound it is asking the user to
   sign, with no opaque blobs.
2. If the user has no Mapae account: collect one EIP-712 `MapaeAccountCreation` consent signature
   and either deploy via the factory or return it in `dependencies`.
3. Collect the EIP-712 `Delegation` signature (domain `{"Mapae", "1", chainId, manager}` — the
   SDK's `DELEGATION_TYPES` are the exact struct set, with `signature` and `args` omitted).
4. Return `{context, delegationManager, dependencies}`.

`wallet_revokeExecutionPermission(context)` maps to `disableDelegation` — already deployed,
reversible, and demonstrated live. The second revocation surface needs no wallet support at all:
the user revokes their Dojang attestation, and every permission gated on it dies at once.

## Status honestly stated

ERC-7715 is a Draft that renamed its entire method surface in January 2026, and its one production
implementation diverges from the current text (request-path `expiry` placement, permission-type
vocabulary). Mapae therefore treats 7715 as a target to stay mappable to, not a dependency: the
SDK builds and signs delegations directly today, and nothing in the contracts would change under
a wallet — the wallet replaces the SDK's signing step, no more.
